# Business Entity Resolution - reproduction guide

Links each Source-1 business to its matching records in the Source-2/Source-3 pool.

1. **Blocking.** Name + address -> hashed character 3-grams (2^15) -> fixed Gaussian random
   projection to 64 dimensions -> L2 normalisation -> exact cosine nearest-neighbour search
   with FAISS (`IndexFlatIP`), **one index per country**. Keep the top-20 hits with cosine >= 0.20.
   At test time the index contains **only the test pool** (Source 2/3 test files).
2. **Matching.** 6 string-similarity features per (query, candidate) pair -> XGBoost.
   A pair is accepted if `p >= 0.93`, or `p >= 0.85` and name Jaro-Winkler `>= 0.90`
   and address fuzz-ratio `>= 0.85`.

No pretrained or external models/data are used.

## Environment

* Python 3.11+ (tested on 3.12.3; the pinned numpy/pandas need >= 3.11). Install: `pip install -r requirements.txt`.
* **GPU strongly recommended for the full dataset.** The pool is ~20M records (US 10.0M, India 8.9M,
  France 1.4M, train + test pools together) and every query is an exact brute-force search.
  The original runs used a GPU build of FAISS (and optionally cuDF) on Colab. The code uses the GPU
  automatically if the installed FAISS has GPU support, otherwise it falls back to CPU, which is
  correct but much slower (hours instead of minutes at full scale; not measured here).
* Disk: the SQLite pool database holds all ~20M pool records (several GB). RAM: the set of test
  pool ids (millions of strings) and one country index are held in memory at once.

## Reproduce the submission (inference with the shipped model)

Run from this folder (`code/business_entity_resolution/`):

```bash
pip install -r requirements.txt
python src/run_pipeline.py --data_dir data --work_dir work
```

This (1) builds `work/pool_data.db`, (2) writes `output/candidate_pairs.tsv` and
`output/matching_results.tsv` (two folders up, next to `code/`; override with `--output_dir`),
and (3) validates them. Then confirm they equal the leaderboard upload:

```bash
python src/compare_outputs.py --generated ../../output/matching_results.tsv --uploaded /path/to/uploaded_matching_results.tsv
python src/validate_outputs.py --matching ../../output/matching_results.tsv --candidate ../../output/candidate_pairs.tsv --data_dir data
```

## Retrain from scratch (optional)

```bash
python src/run_pipeline.py --data_dir data --work_dir work --retrain --xgb_device cuda   # or cpu
```

Trains on the first 40,000 rows of `train_source1.tsv`, validates on the next 10,000, writes
`work/xgb_entity_model_retrained.json` and `work/validation_report.json` (precision / recall / F0.5
for the p>=0.75 rule and for the final rule, plus candidate recall), then runs inference with the
retrained model. The shipped model file is not overwritten. Stages can be run separately with
`--stage {db,train,predict,validate}`.

## Reproducibility notes (please read)

* **Exact reproduction = shipped model.** XGBoost training on a GPU is not guaranteed bit-identical
  across hardware/library versions, so a retrained model can differ slightly from the shipped one and
  change a few predictions. Inference with the shipped model is deterministic given the same data.
* **Database cleaning backend.** The original database was built with cuDF; without cuDF the
  identical cleaning is done with pandas/`re`. They agree on ASCII text; behaviour of the regex `\w`
  on non-ASCII characters (e.g. French accents) may differ between the two backends. This was not
  verified on the real data. Build the database on a machine with cuDF to match the original run.
* **Hard-coded design choices** (all in `config.py`): countries are blocked hard (a match is only
  searched within the same country); test inference indexes test-pool records only; the model was
  trained on candidates retrieved from the combined pool (train + test pool records, unlabeled).
* Files are written with Python's `csv` defaults (tab-separated, CRLF line endings), as in the
  originally uploaded files.

## Provenance of the code (`notebooks/`)

The scripts above are a cleaned, tested re-organisation of two Colab notebooks:

| Pipeline step | Notebook |
|---|---|
| Database, features, FAISS, XGBoost training, hold-out validation (F0.5 = 0.8344) | `nb1_training_and_first_inference.ipynb` (cells 3-6, 8) |
| First test inference - indexed the *whole* pool, so it returned training-pool ids and **failed** the submission validator | `nb1...` cell 7 (superseded) |
| Final test inference (test-only index, top-20, cos >= 0.20, thresholds 0.93 / 0.85 rescue) - **source of the submitted file** | `nb2_final_inference.ipynb` |

The refactored scripts were checked against the original notebook code on identical inputs, the database contents, the feature values, the embeddings, the decision rule and both output TSVs were
byte-/value-identical. The notebooks are kept only for transparency; `src/` is the production code for the pipeline.
